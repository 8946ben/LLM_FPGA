性能提升的三个直接原因

8 lanes每拍计算 8 个 BF16 对应的 FP32 乘积一行 896 项点积 → 112 个权重 beat
II = 1同一累加器隔 16 拍才再次更新覆盖 FP32 加法反馈延迟，消除原来的逐项依赖瓶颈
重叠下一行点积与上一行归约并发权重读取、点积、归约、penalty/argmax 分为 DATAFLOW 进程

按 8/II 计算，理想点积项吞吐由 0.125 项/拍变为 8 项/拍，即 64×。这是稳态结构上限，未计入访存、行切换及归约开销，不能替代板测加速比。

03 / WHAT CHANGED

V2 具体做了这八项优化

计算和访存改变单次推理速度；接口、数值与部署改进让结果可验证、模块可交付。

01 / COMPUTE综合确认

单路点积 → 8 路并行乘加

1 multiplier + 1 adder→8 multipliers + 8 adders

按 hidden 维度展开 8 个 lane。每个 128-bit 权重字拆出 8 个 BF16，与 8 个缓存激活并行运算。这里的“乘加”是分别舍入的 FP32 乘法和加法，未采用融合 FMA。

证据：HLS 运算单元与 II 报告 ↗

02 / SCHEDULINGachieved II = 1

16 路交错累加，拉开反馈距离

每项依赖同一 accumulator→partial[lane][word & 15]

每 lane 维护 16 个 FP32 部分和；连续周期更新不同槽位。相同槽位隔 16 拍复用，为加法流水留出完成时间。8 × 16 共 128 个部分和，最后按固定树归约。

证据：dot_product_rows / reduce_partials ↗

03 / MEMORY128-bit 接口确认

宽字连续读取 + 8-bank 激活缓存

32-bit M_AXI / 单端口缓存→128-bit / 8 banks

hidden 只预载一次，按 lane 分 bank，满足每拍 8 路读取；权重 reader 顺序送入深度 128 的 FIFO。权重口配置 burst=16、outstanding=16。四个逻辑 master 汇入同一个 HP2，并非四条独立 DDR 通道。

证据：接口宽度与 HP2 连接 ↗

04 / DATAFLOW源码与 RTL 验证

双上下文 FIFO，让行间归约与点积重叠

本行计算完，再处理下一行→dot(n+1) ∥ reduce(n)

点积、归约和策略处理独立运行。256-bit × 32 深度的 context FIFO 容纳两行部分和快照，每行 16 个 slice；避免每一行都串行等待归约，也避免直接拉出 4096-bit 内部总线。

证据：run_dataflow / context_fifo ↗

05 / NUMERICS8-step 严格通过

BF16 存储，FP32 一直保留到决策

FP16 输入 / raw 先舍入 FP16→BF16 输入 / FP32 policy

权重来自原始 safetensors 的 canonical BF16；点积、penalty、argmax 保持 FP32，去掉 argmax 前的 FP16 舍入。固定归约树和每步 FP32 舍入，软件 reference 与 RTL 逐位对齐。BF16 与 FP16 均为 16 位，权重大小没有减半。

06 / INTEGRATION模块实现，整体待集成

共享词表接口，生产路径避免 logits 写回

独立 FP16 资产 / 专用接口→shared_vocab_weight / 双 run_mode

接口采用共享 BF16 词表布局，供 Embedding/LM Head 复用；避免复制约 259.66 MiB 的收益需在系统集成时兑现。Prefill/Decode 均只消费最后一个有效 hidden row。保留原有 PL penalty/argmax 和可选 logits；V2 默认关闭写回，已验证零 logits 写事务。

04 / EXPLORE THE MECHANISM

为什么交错累加能把 II 降下来？

拖动权重 word 序号，查看一个 lane 中被更新的槽位。8 个 lane 同时执行同样的槽位选择。

16 个部分和，轮流更新

word 0 / 111
slot = 0 & 15 = 0

这是点积循环连续供数时的调度示意，word 序号不等同于整次任务的实测 cycle。相同槽位相邻两次更新间隔 16 个迭代；旧版则每项都回到同一个 accumulator。

行间也能并行

点积进程
行 0行 1行 2
归约进程
行 0行 1
概念时序 · 横向为推进方向，宽度不表示实测时长

每行 896 个元素拆成 112 个宽字。点积进程完成本行后，把 16 份 256-bit 部分和送入 context FIFO；归约进程取走快照时，点积进程可开始下一行。

降低 II 和增加 lane 是两个独立改进：前者减少启动间隔，后者增加每次启动的工作量。访存与行边界开销决定最终效果。
05 / NUMERICAL CONTRACT

数值语义也升级了，不能只比较旧 token

更换存储格式与浮点求和顺序后，需要与 V2 reference 对齐。这里的“通过”是严格逐位校验。

V1 的决策路径

  1. FP16 hidden / weight
  2. FP32 单 accumulator 顺序求和
  3. raw dot → FP16 舍入
  4. 转回 FP32 → penalty → argmax

旧版已在 PL 内完成 penalty/argmax，也支持关闭 raw logits 写回；这些能力是 V2 的延续，不是新增的加速来源。

V2 的决策路径

  1. BF16 hidden / shared vocab weight
  2. FP32 × 8 lanes × 16 slots → 固定归约树
  3. raw dot 保持 FP32 → penalty → argmax
  4. AXI-Lite 返回 token / FP32 score；同分取较小 ID

debug 可写出 penalty 前的 FP32 logits：151,936 × 4 = 607,744 B；生产关闭时不产生该写流量。

已有可见差异：step_07

旧 FP16-round 语义100013
V2 FP32 语义100048

这是数值语义差异，不应直接判为硬件随机错误。现有 hidden trace 由旧 FP16 trace 转成 BF16，尚不能代表 M06 V2 原生端到端输出。

归约树与 reference 已闭环

旧 Python 最后的 8-lane 合并顺序与 C++/RTL 不同；2026-10-09 改成相邻 lane pair 归约。硬件未修改，reference/golden 按冻结合同重算。

2026-10-10 的 8-step 生产/debug 全部通过 token、score bits、CRC 与全量 logits SHA256 校验；不是放宽容差后通过。

06 / WEIGHT LOADING

权重加载的优化，服务于开发迭代

权重常驻 DDR 后可以跨 token 复用；这里比较的是主机到板上 DDR 的大文件装载阶段。

2026-10-10 修复版实测
30 min → 8.36 s

相对本轮 JTAG 大文件装载约 215×；不是相对旧版已具备的 TCP 上传，也不包含整次初始化。旧版历史 FP16 网口测速不混入本次 BF16 数据。

文件大小 259.65625 MiB，实测 31.06077 MiB/s。端到端 elapsed 包含连接、逐块回应和最终全 DDR CRC；主机 SHA256 扫描、PS 初始化、小 ELF 下载及额外 JTAG sentinel 时间另计。

加载成功有四道校验

01canonical BF16 SHA256
02每块 DDR 回读 CRC32
03整份 DDR CRC32
04首尾 sentinel

6 项错误路径板测通过，包含坏 CRC、分段请求/重复序号、超大块、提前 COMMIT、中途断线和最终 CRC 错误；失败后整份重传。

10 月 12 日复跑上传记录：8.410 s / 30.874 MiB/s，PASS。权重大小与 SHA256 一致。
