4. Python 参考实现

对应目录：qwen25_0p5b_python_reference/

Golden trace（第 3 篇）只是一堆静态的 .npy 数据，而本目录的任务是：把 trace 背后的推理流程固定为可读的 Python 代码。有了这些参考实现，FPGA 侧每实现一个模块，就能找到一份语义完全等价的 Python 代码来逐模块对齐，做到「先比数值，再谈性能」。

这里的每个脚本都扮演不同角色：有的负责「生产」trace，有的负责「复现」推理流程，有的负责「定义」模块数学语义，还有的负责「裁决」FPGA 结果是否正确。写 HLS 之前建议先把它们都跑通一遍。

文件一览

文件作用
run_full_generate_trace.py 完整推理入口，基于 HuggingFace model.generate()（greedy、do_sample=False、output_scores=True）。依赖插桩版 Transformers，通过环境变量 QWEN2_FPGA_RECORD=1 / QWEN2_FPGA_RECORD_DIR 开启记录，写出 metadata.json + 每步 vocab logits 到 generation_token_vocab_logits/。
manual_prefill_decode.py 不调 generate()，手写 prefill→decode 循环（eager attention、KV cache 逐 token、argmax），是最接近 FPGA runtime 需要复现的显式流程。--save-scores 可导出每步 FP32 logits。
qwen2_module_reference.py 模块级 PyTorch 参考实现：RMSNorm（FP32 内部计算后 cast 回原 dtype）、Linear、RoPE、GQA repeat_kv、eager attention（softmax 用 FP32）、SwiGLU MLP、lm_head；layer_flow_order() 给出 FPGA 模块的实现顺序。
qwen2_generate.py 纯手写推理：不实例化 AutoModelForCausalLM，直接读 model.safetensors + config.json，用模块函数拼出完整 forward/decode，用于验证模块参考实现的正确性（含 tokens/s 统计）。
lm_head_cpu_reference.py 模块 16（lm_head + token 选择）的 CPU golden 验证器：lm_head_chunked 按 vocab 4096 行分块、FP32 累加算 W@h；apply_repetition_penalty（HF 语义：负乘正除）+ greedy_argmax（tie 取最小 id）。
snapshots/modeling_qwen2_fpga_instrumented.py 插桩后的 Qwen2 模型源码快照：在每层各算子点调用 recorder 导出中间张量。
snapshots/fpga_recorder.py 线程安全的 recorder：每次 forward 生成一个 step_NNNN 目录，按 layer_NN 子目录存 .npy，附 metadata.jsonl 记录每个张量的 shape/dtype。

两条推理路径

目录里有两条互相印证的推理路径，这是 correctness-first 方法的核心：

路径 A（generate()）:  run_full_generate_trace.py
    └── 调 HuggingFace generate() + 插桩 recorder → 产出 golden trace

路径 B（手写循环）:    manual_prefill_decode.py / qwen2_generate.py
    └── 手写 prefill→decode，显式维护 KV cache → 复现 FPGA runtime 行为

验证：两条路径的 8 步 token ids 完全一致

路径 A 用来「生产」数据，路径 B 用来「复现」FPGA 上将要执行的显式流程。FPGA 侧的开发对标的是路径 B 的行为，用路径 A 的 golden 数据做对齐。

lm_head_cpu_reference：模块 16 的裁决者

lm_head_cpu_reference.py 是模块 16（LM Head）验证链条的核心。它逐 step 比对 golden trace 中的 lm_head_input / vocab_logits 与 generation_token_vocab_logits/ 中导出的每步 logits，判定标准如下：

比对项通过阈值
processed scores（生成策略处理后的 scores）max_abs ≤ 2e-6
matmul（FP32 累加 W@h 与 trace logits）cosine ≥ 0.999
top5 重叠≥ 4

加上 --output-dir 参数可以把 FP32 计算的 logits 导出成文件，产物在 artifacts/module16_cpu_logits/ 下（00..07_computed_logits_fp32.npy），供后续 HLS / 板端验证直接复用。

argmax 在 FP16 LM Head 输出上执行，而不是在 FP32 accumulator 上。这一点是模块 16 最容易踩的坑：FPGA / CPU 参考实现都必须先算 FP32 累加，然后把结果 cast 回 FP16，再对 FP16 logits 做 argmax。step 7 时 token 100013 与 100048 转成 FP16 后同为 20.203125，此时必须按 torch.argmax 的规则选择位置较前的 100013，否则会选出错误的 token。

H200 服务器复现

在 H200 服务器上可以用如下命令完整复现手写 prefill/decode 路径（对应 manual_prefill_decode.py）：

# conda 环境
source /data3/output/conda_envs/qwen25_fpga_transformers/bin/activate  # 或 conda activate

# 必要的环境设置（避免用户站点包与编码问题）
export PYTHONNOUSERSITE=1
unset PYTHONUSERBASE
export PYTHONIOENCODING=utf-8

# 模型路径：/data3/models/Qwen2.5-0.5B-Instruct
python manual_prefill_decode.py \
    --model-path /data3/models/Qwen2.5-0.5B-Instruct \
    --record-dir <输出目录> \
    --max-new-tokens 8 \
    --save-scores

预期输出：

response = 我是Qwen，由阿里云开发
generated_ids = [104198, 48, 16948, 3837, 67071, 102661, 99718, 100013]
generate() 路径（run_full_generate_trace.py）在同一环境下也已验证，两条路径产出的 token ids 完全一致——这正是后续所有模块级验证能放心进行的前提。
