3. Golden Trace 数据集

本篇介绍整个工程的「标尺」——golden trace 数据集。所有 FPGA 模块（HLS 内核、板端实现）的正确性，都要拿自己的输出和这里的 golden .npy 文件逐项比较。理解了 trace 的组织方式，后面的 Python 参考实现、HLS 模块设计就都顺理成章了。

什么是 golden trace

golden trace 是对 一次完整推理过程的全部中间张量 的记录。它由插桩版 HuggingFace Transformers 生成：修改 modeling_qwen2.py，并配合 fpga_recorder.py，在 FP16 eager 推理的每一步，把 RMSNorm、Q/K/V 投影、RoPE、KV cache、softmax、MLP 等每一个中间量都保存成 .npy 文件。

有了 golden trace，验证 FPGA 模块就不再是「跑一遍看结果像不像」，而是逐张量、逐 bit 级比对：任何模块算错了，都能立刻定位到出错的具体算子。

当前 trace 摘要

model             = Qwen/Qwen2.5-0.5B-Instruct
prompt            = 你好，请用一句话介绍你自己。
input_token_count = 36
max_new_tokens    = 8
decode            = greedy（do_sample=False, use_cache=True, attn_implementation=eager）
response          = 我是Qwen，由阿里云开发
generated_ids     = [104198, 48, 16948, 3837, 67071, 102661, 99718, 100013]
files             = 7386
step_dirs         = 8（1 个 prefill + 7 个 decode）
layer_dirs        = 192（8 步 × 24 层）

一次生成共 8 步：1 次 prefill（一次过完整的 36 个 prompt token）加 7 次 decode（每次只算 1 个新 token，KV cache 逐步增长），采用贪心解码（greedy），总共生成 8 个 token。

目录结构

qwen25_0p5b_instruct_full_generation_trace/
├── 00_prefill_full_prompt/          # 完整 prompt 的 prefill forward
├── 01_decode_token_01/              # 第 1 个 decode 步（KV cache 逐步增长）
├── 02_decode_token_02/
├── ...                              # 03 ~ 06 略
├── 07_decode_token_07/              # 第 7 个 decode 步
├── generation_token_vocab_logits/   # 每步用于选 token 的 FP32 processed scores（8 个 .npy）
├── metadata.json                    # prompt、input ids、generated ids、输出文本、trace 元信息
├── name_mapping.json                # 原始 recorder 文件名 → FPGA 友好文件名映射
└── flightllm_test_demo/             # FlightLLM FPGA LLM demo 参考工程
条目说明
00_prefill_full_prompt/对完整 prompt（36 个 token）做一次 prefill forward，并保存全部中间量
01_decode_token_01/ ~ 07_decode_token_07/逐 token 的 decode 步，每步只输入 1 个 token，KV cache 逐步增长
generation_token_vocab_logits/每一步用于选出下一个 token 的 FP32 processed scores，共 8 个 .npy
metadata.json记录 prompt、input ids、generated ids、输出文本以及 trace 元信息
name_mapping.json原始 recorder 文件名到 FPGA 友好文件名的映射表
flightllm_test_demo/FlightLLM FPGA LLM demo 参考工程（作为工程组织参考）

每个 step 目录里有什么

每个 step 目录（prefill 或某个 decode 步）包含该步的整体输入/输出文件，以及 24 个 transformer block 的子目录：

00_prefill_full_prompt/
├── model_input_token_ids.npy        # 本步输入的 token ids
├── lm_head_input.npy                # lm_head 的输入 hidden state
├── lm_head_vocab_logits.npy         # lm_head 输出的全词表 logits
├── final_rmsnorm_input.npy          # 最后一层 RMSNorm 的输入
├── final_rmsnorm_output.npy         # 最后一层 RMSNorm 的输出
├── metadata.jsonl                   # 本步的元信息（逐行 JSON）
├── layer_00_transformer_block/      # 第 0 层 transformer block
├── layer_01_transformer_block/
├── ...                              # 02 ~ 22 略
└── layer_23_transformer_block/      # 第 23 层 transformer block

每个 layer_XX_transformer_block/ 子目录里约有 40 个 .npy，覆盖该层完整的数据流：

  • RMSNorm 的输入 / 输出；
  • Q / K / V 投影结果；
  • RoPE 前后的 Q / K（含 cos / sin）；
  • KV cache 更新后的内容；
  • GQA repeat 后的 K / V；
  • 加 mask 前后的 attention scores；
  • softmax 后的注意力权重；
  • 加权 value 求和（attention 输出）；
  • attention 输出投影、残差相加；
  • MLP 全链路：gate / up 投影、SiLU、gate*up、down 投影。

golden tensor 形状示例

下面列出几个典型的 golden tensor 及其形状，帮助你建立对数据规模的直觉：

张量文件所在步骤形状说明
model_input_token_ids.npyprefill(1, 36)完整 prompt 的 36 个 token id
layer0/attention_input_after_rmsnorm.npyprefill(1, 36, 896)第 0 层 attention 的 RMSNorm 输出（896 维 hidden）
attention_qk_scores_after_mask.npyprefill(1, 14, 36, 36)14 个 Q head，36×36 的因果 mask 后 scores
attention_k_cache_after_update.npyprefill(1, 2, 36, 64)GQA：2 个 KV head，64 维 head_dim
model_input_token_ids.npydecode 第 1 步(1, 1)decode 每步只输入 1 个新 token
attention_qk_scores_after_mask.npydecode 第 1 步(1, 14, 1, 37)KV cache = 36 + 1 = 37
attention_qk_scores_after_mask.npydecode 第 7 步(1, 14, 1, 43)KV cache 增长到 36 + 7 = 43
prefill_next_token_vocab_logits.npygeneration_token_vocab_logits/(1, 151936)全词表（151936 词）的 FP32 processed scores

注意 decode 步的 scores 最后一维从 37 增长到 43——这正是 KV cache 逐步增长的直接体现。

数据格式说明

golden trace 全程为 FP16 推理（GPU，eager attention）。.npy 文件保持推理时的原始 dtype：

  • FP16 张量按 float16 原样存储；
  • BF16 张量在保存时会被转换为 FP32 存储；
  • generation_token_vocab_logits/ 下用于选 token 的 processed scores 为 FP32。

FPGA 模块实现顺序（18 步）

golden trace 逐张量覆盖的特性，决定了 FPGA 模块可以按数据流顺序逐个实现、逐个对齐。推荐的实现顺序如下：

  1. RMSNorm
  2. Linear Q/K/V projection
  3. RoPE
  4. KV cache update
  5. GQA KV repeat
  6. QK matmul and scale
  7. causal mask
  8. softmax
  9. attention weighted value sum
  10. attention output projection
  11. residual add
  12. MLP RMSNorm
  13. MLP gate/up projection
  14. SiLU
  15. gate*up
  16. MLP down projection
  17. final RMSNorm
  18. lm_head logits
建议第一个验证目标：00_prefill_full_prompt/layer_00_transformer_block/attention_rmsnorm_input.npy 和 attention_rmsnorm_output.npy——即第 0 层 prefill 的 attention RMSNorm。验证节奏：先做 layer 0 prefill，再做 layer 0 decode，最后扩展到全部 24 层。

注意事项

本仓库保存的是 0.5B 小模型的 demo trace，不是完整 Qwen2.5-7B 的 trace。golden tensor 的用途是 correctness verification（正确性验证），性能优化应放在结果对齐之后。另外，仓库内包含约 80MB 的 FlightLLM bitstream；后续若引入更多大 trace，建议使用 Git LFS 或外部 artifact storage 管理。
