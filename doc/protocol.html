6. LMH1 网络协议

LMH1 是上位机（CPU / Orin）与 FPGA 板之间的一个 TCP 应用层协议，用来把 LM Head（模块 16）的计算卸载到 FPGA 上执行。上位机先把 151936×896 的 FP16 权重上传到板端 DDR，之后每生成一步，把当前 hidden 向量和历史 token bitmap 发给板端，板端完成矩阵乘、repetition penalty 和 argmax 后，把选中的 token id 回传。

  • 默认板端地址：192.168.8.190，端口 19016。
  • 协议文档：module16_lm_head_hls/NETWORK_PROTOCOL.md。
  • 板端（PS 侧）实现位于 realFpga/ 工程。

Python 参考实现

在真板之前，协议的全部行为都先在 module16_lm_head_hls/net/ 目录下用纯 Python 实现并测试：

文件行数职责
net/lmh_protocol.py111帧头打包/解包、CRC32、opcode 与 flags 常量定义
net/cpu_client.py145上位机客户端 LmHeadClient，负责分块上传权重、发送 RUN_TOKEN
net/fpga_server_emulator.py231板端 NumPy 模拟器，行为与真板服务端一致，可本机回环测试

会话生命周期

上位机 (CPU/Orin)                          FPGA 板 (192.168.8.190:19016)
      │                                          │
      │──── TCP 连接 ────────────────────────────│
      │                                          │
      │──── LOAD_WEIGHT (分块, 约 260 MiB) ─────►│  仅一次, 写入 DDR 预留区
      │◄─── ACK (每块响应) ──────────────────────│
      │                                          │  LAST_CHUNK 校验完成 → READY
      │                                          │
      │──── RUN_TOKEN (hidden + history) ───────►│  可多次
      │◄─── status + token (+ logits) ───────────│  WANT_LOGITS 时附带 151936 个 logits
      │         …… 重复多步 ……                   │
      │                                          │
      │──── 可选 READ_LOGITS ───────────────────►│
      │                                          │
      │──── 关闭连接 ────────────────────────────│  权重跨连接保留

要点：

  • LOAD_WEIGHT 只执行一次，约 260 MiB 的 FP16 权重分块上传。
  • 之后可以多次 RUN_TOKEN，每步对应一次 decode。
  • 是否随 RUN_TOKEN 响应返回全部 logits，由请求里的 WANT_LOGITS flag 控制。

帧头格式（24 字节，小端）

每一帧（请求和响应都一样）以 24 字节帧头开头，struct 格式为 <4sHHIIII：

字段类型含义
magic4 字节固定为 'LMH1'，用于快速识别协议帧
versionu16协议版本，当前 = 1
opcodeu16操作码（见下表）
request_idu32请求编号，响应原样带回，便于对账
flagsu32标志位（见下表）
payload_bytesu32payload 长度（字节）
payload CRC32u32payload 的 CRC32（IEEE），校验失败直接拒绝

响应帧的 opcode 规则：

  • 正常响应：opcode = 请求 opcode | 0x8000。
  • 错误响应：opcode = 0xFFFF。

opcode 一览

opcode值方向含义
LOAD_WEIGHT1请求上传一块权重数据
RUN_TOKEN2请求执行一步 LM Head 计算
PING3请求探活 / 查询权重加载状态
正常响应请求值 | 0x8000响应如 LOAD_WEIGHT 的响应为 0x8001
错误0xFFFF响应帧非法、CRC 错误等

flags 位定义

位名称含义
bit0ENABLE_REPETITION_PENALTY启用 repetition penalty（配合 RUN_TOKEN payload 中的系数和 history bitmap）
bit1WANT_LOGITS要求 RUN_TOKEN 响应附带全部 151936 个 FP16 logits
bit2FIRST_CHUNKLOAD_WEIGHT 的第一块
bit3LAST_CHUNKLOAD_WEIGHT 的最后一块，触发完整性校验并进入 READY

LOAD_WEIGHT：上传权重

payload 以 24 字节前缀开头（struct <QIIQ），随后紧跟本块的 FP16 权重数据：

字段类型含义
total_bytesu64权重总字节数
hidden_sizeu32隐藏维（896）
vocab_sizeu32词表大小（151936）
offsetu64本块数据在整体权重中的字节偏移

上传规则：

  • 必须从 offset = 0 开始，连续、按序上传，不允许跳块。
  • 收到带 LAST_CHUNK 的块后，服务端校验末尾偏移 == total_bytes，通过后进入 READY 状态。
  • Python 客户端默认按 4 MiB 分块；真板服务端单块最大支持 16 MiB（流式直写 DDR 预留区）。

RUN_TOKEN：执行一步计算

请求 payload

前缀 struct <IIfI（16 字节），随后是 hidden 向量和 history bitmap：

字段类型含义
hidden_sizeu32隐藏维（896）
vocab_sizeu32词表大小（151936）
repetition_penaltyFP32重复惩罚系数
history_wordsu32history bitmap 的 u32 字数
hiddenFP16 × 896当前步的 hidden 向量，896×2 = 1792 字节
history bitmapu32 × 4748已生成 token 的位图，4748×4 = 18992 字节

响应 payload

前缀 struct <IIfI（16 字节）：

字段类型含义
statusu320=OK；1=NOT_READY（未加载权重）；2=BAD_REQUEST
selected_tokenu32argmax 选中的 token id
selected_scoreFP32选中 token 的分数
logits_bytesu32追加的 logits 字节数（未开 WANT_LOGITS 时为 0）
logits（可选）FP16 × 151936WANT_LOGITS 时追加，151936×2 = 303872 字节 raw logits

PING：探活与状态查询

PING 无 payload，响应为 struct <IIQ：

字段类型含义
hidden_sizeu32隐藏维
vocab_sizeu32词表大小
weight_bytesu64已加载的权重字节数，可据此确认权重是否已就绪
校验与鲁棒性：每一帧的 payload 都带 CRC32，校验错误直接拒绝该帧。真板服务端是「单连接多帧」状态机，可以跨 TCP pbuf 拼接帧头和 payload（TCP 是流式协议，一帧可能被拆成多个包到达）；权重加载完成后跨连接保留，断线重连无需重新上传。

python tools/run_module16_board_trace.py \
    --host 192.168.8.190 --port 19016 \
    --load-weight artifacts/model.embed_tokens.weight.fp16.npy \
    --fixture-root artifacts/module16_hls_fixtures \
    --return-logits
